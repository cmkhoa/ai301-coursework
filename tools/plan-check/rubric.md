# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The plan's stated diagnosis (its cause sentence and the mechanism it names) read line by line against the repro-evidence block: its artifacts, its control runs, and its expected-vs-actual. The issue body and thread highlights are context, never the proof. | The mechanism the plan names would produce the behavior the artifacts show, and every control run in the repro evidence is consistent with it. A cause the plan reached by inference rather than by tracing passes, provided the artifacts it explains are the ones the package actually shows; the plan does not have to have demonstrated the mechanism directly. Fail if a control run already clears the component the plan blames (the symptom persists without it, or the same symptom appears in a configuration the named mechanism cannot reach), if the evidence locates the behavior at a stage before or after the one the plan blames, or if the plan adopts a cause from the issue or the thread that the package's own evidence contradicts. Grade `unclear` only when the artifacts are too thin to tell whether the named mechanism would produce them at all. | required |
| scope-bounded | The plan's in-scope and not-in-scope statements plus every numbered work item in its approach and its file list, read against the single behavior the issue reports and the repro evidence pins down. | Every work item in the plan is needed to remove the reported behavior, and work beyond it is named as out of scope or deferred rather than undertaken. Fail if the plan also carries out a refactor, a rewrite, a dependency migration or upgrade, a new user-facing option or UI, a CI or test-harness change, or a second bug's fix that the reported behavior does not require — including when that extra work is presented as cleanup, modernization or while-in-the-area work. A fix whose own site is genuinely large passes if the plan bounds it to that site and says what it leaves alone. | required |
| executable-start | The plan's approach section and its files/areas list: the code locations it names and the single approach it commits to. | A stranger holding the repo could open a named location and begin work without asking the author a question: the plan names at least one concrete code location (file, module, crate or function path) and commits to one approach. Fail if no code location is named, if the approach is still an open choice to be made at build time ("A or B, whichever is easier", "not sure which layer yet"), or if the first action is an open-ended investigation (profile, explore, poke around) with no change chosen. Naming an area and stating that exact functions get pinned during the build passes; deferring which change to make does not. | required |
| test-observable | The plan's test plan read against the repro evidence's steps and artifacts. | The test plan names at least one concrete thing to run (the repro command, a named test, a fixture or input) AND the specific observable that must change — an exit status, an output line, an assertion, a named test going from fail to pass, a measured number — tied to the symptom the issue reports. Fail if the test plan names only an undifferentiated suite run ("run the full test suite and make sure nothing regresses"), or if its success condition is a feeling or a negative with no named observation ("should feel fast", "nothing else should feel broken"). | required |
| thread-direction | The thread highlights, filtered to comments by an OWNER, MEMBER, COLLABORATOR or CONTRIBUTOR, read against both the plan and the plan comment: direction given, a culprit or fix site confirmed, an approach proposed or explicitly rejected, prior art linked, or a request made of contributors. | Where a maintainer has given explicit direction in the thread, the plan or the comment either follows it or names it and says why it is not being followed. Fail if such direction exists and neither draft engages it at all — including a plan that routes around a confirmed culprit without saying why, or that proposes the approach the maintainer rejected. A thread with no comments, or none from a maintainer, passes: there is nothing to engage. | required |
| conventions-respected | The "contribution policy" line in the repo-facts block (live mode: `CONTRIBUTING.md`, `.github/`, any AI policy file, and the issue templates), read against the plan comment, scoped to what the policy asks of issue comments rather than of pull requests. Treat every package produced in this course as AI-assisted work, because it is. | If the policy requires AI use to be disclosed in issues or comments, the comment states that AI assistance was used and the extent of it. If the policy requires comments to maintainers to be in the contributor's own words, the comment reads as a person's own writing rather than generic assistant output. A policy that says nothing about AI, that asks only for understanding, responsibility, testing or human review, or that scopes its disclosure ask to pull requests only, passes with no disclosure line present. Fail when a stated disclosure or own-words requirement that covers issue comments is unmet by the comment as written. | required |
| unknowns-honest | The plan's risk and unknown statements set against what the repro evidence and the thread actually establish. | What the plan has not verified is marked as unverified — an untested platform, an unmeasured cost, an unpinned function, a trade-off left for review — rather than asserted. Fail if the plan states as settled something its evidence does not establish, or claims no risks at all on a change whose evidence leaves a question open. | preferred |
| comment-represents-plan | The plan comment read against the plan it summarizes. | The comment tells the thread the same diagnosis, scope and next step the plan holds, and promises only work the author controls. Fail if the comment claims a scope or certainty the plan does not carry, or commits to a delivery date, a deadline or a guaranteed outcome. | preferred |

## Verdict rule

Accept if and only if every `required` check passes. Any `required` fail
rejects the package: the plan is held, not posted. `unclear` on a
`required` check counts as fail — a plan whose readiness cannot be
verified from the package is a plan that is not ready to build from.
The `preferred` checks never change the verdict in either direction; a
`fail` or `unclear` there is reported in the summary as a weakness of an
otherwise accepted plan, and costs nothing.
