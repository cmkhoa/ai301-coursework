# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The environment record in the repro report (its `Environment:` line or equivalent prose), read against the versions and platform the issue names in its body/title and against the "bug reports" template asks in the repo-facts block. | The report names the version or build of the software under test AND the machine it ran on (OS, or the runtime/host the behavior depends on), AND any further setup factor the issue itself names as part of the failing configuration (driver, backend, shell, build profile, install method). Fail if the report gives none of these, or omits a factor the issue names as decisive for the behavior. A record that differs from the issue's target still passes here; whether the difference was declared is graded by `deviation-declared`. | required |
| steps-rerunnable | The steps section of the repro report: the starting state, every command, config file, input document or script the steps name, and whether each of those inputs appears in the report or is fetchable from the issue or the repo. | A stranger holding the stated environment could execute the steps as written and arrive at the trigger: the starting state is stated, every input the steps depend on is shown in the report or publicly fetchable, and no step rests on private or unshared material. Fail if any input the outcome depends on is unavailable to the reader (a private repo, an unshared config, "our internal setup"), or if the steps omit a factor the issue names as necessary to trigger the behavior. | required |
| artifact-shows-issue | The report's artifacts (output excerpts, logs, screenshots, measurements) read line by line against the specific behavior the issue describes: its error text, exit status, or named symptom. | Either the artifact exhibits the issue's own failure — the same error, exit status, or symptom the issue reports — or the report states plainly that the attempt did not reproduce and its artifacts show what happened instead. Fail if the artifacts show a different failure from the one reported (a graceful validation error where a crash was reported, an adjacent symptom, a compile error where a runtime error was reported), show only that the software ran at all (a version banner, a session list), or are absent while the report asserts the behavior happened. | required |
| deviation-declared | The version, command form, input shape and platform actually exercised (the report's environment record and its commands) set against the target the issue states (the issue's version line, its reproduction commands, its platform). | Either the run matches the issue's stated target, or every difference is named in the report as a difference. Fail if the package ran an older or different version, a different command or syntax than the issue's, a different input shape, or a different platform, without saying so; fail also if an artifact is trimmed or altered so that it differs from the issue's without the report noting it. Naming the difference is enough to pass; the report does not have to justify it. | required |
| claims-match-evidence | Every factual assertion in the claim comment and the repro report — root causes, "I verified", "guaranteed reproducible", "it also happens on X" — set against the artifacts the package actually shows, including its own stated expected-vs-actual. | Every assertion is either backed by a shown artifact or marked in the text as a hypothesis or a next step. Fail if the package asserts a cause, a verification, or a scope no shown artifact supports (a diagnosed race with no transcript, a generalization to a build that was never run), or if the stated expected/actual contradicts the artifact printed beside it. | required |
| claim-specific-intent | The candidate claim comment, read against this issue's own content. | The claim names something specific to this issue — the behavior it reproduced, a named file, function or code path, or a concrete next investigation step — and says what the author will do next. Fail if the comment carries only agreement, enthusiasm or a report of personal suffering ("+1", "same here", "this has been driving me crazy"), or if it is interchangeable text that would sit unchanged on any other issue in any other repo. | required |
| claim-promises-only-work | The candidate claim comment. | The claim commits only to investigation and to reporting back. Fail if it promises a fix or a delivery date, offers a guarantee, demands assignment or asks for the issue to be reserved, or states certainty about a cause whose evidence the package does not show. | required |
| conventions-respected | The "contribution policy" line in the repo-facts block (live mode: `CONTRIBUTING.md`, `.github/`, any AI policy file, and the issue templates) read against both candidate comments. Treat every package produced in this course as AI-assisted work, because it is. | If the policy requires AI use to be disclosed in issues or comments, at least one of the two comments states that AI assistance was used and the extent of it. If the policy requires comments to maintainers to be in the contributor's own words, the comments read as a person's own writing rather than generic assistant output. A policy that says nothing about AI, or that asks only for understanding, responsibility, testing or human review without a disclosure requirement, passes with no disclosure line present. Fail when a stated disclosure or own-words requirement is unmet by the comments as written. | required |
| control-contrast | The report's artifacts. | The report shows a contrasting run — the working case, the same command without the trigger, or the issue's own known-good variant — that isolates the factor under suspicion. | preferred |
| template-asks-met | The "bug reports" template asks in the repo-facts block set against the repro report. | The report supplies the items the repo's own bug template asks reporters for (version, OS, install method, minimal input, command, actual and expected behavior). | preferred |

## Verdict rule

Accept if and only if every `required` check passes. Any `required` fail
rejects the package: it is held, not posted. `unclear` on a `required`
check counts as fail — proof that cannot be verified from the package is
proof that is not ready to go upstream — with one exception, which is the
claim-only live draft described in `SKILL.md`: checks whose evidence is
the repro report are reported `unclear` with the evidence line `not yet
applicable: claim-only draft` and are left out of this rule entirely, so
the verdict then answers only whether the claim comment is ready. The
`preferred` checks never change the verdict in either direction; they say
how strong an accepted package is, and a `fail` or `unclear` there costs
nothing.
